# orbit-site agent instructions

Only what the global instructions and shared skills do not already cover.

## What this project is for

Orbit's public website: the door, the demo flight, the install page, the
imported docs and the information page, as plain HTML, CSS and ES modules
with no build step. `README.md` has the layout. The site *describes*
Orbit; the software itself, its installer and its docs' source live in
`ai/orbit` and `ai/orbit-launcher`, and a change there that alters what the
public is told belongs here too (orbit `AGENTS.md`). Anything that is not
the site -- a feature, an install step's behaviour, a doc's wording --
belongs in those repositories, not here. The docs under `assets/docs/` are
generated by the import and are never edited by hand.

## Hosts: GitLab first, GitHub is the mirror and the host

Since 2026-10-08 (docs/plans/gitlab-migration.md) the project lives at
`gitlab.tomlawson.io/ai/orbit-site` (project id: see the plan once the
import has run): issues, merge requests, protected branches and the CI gate
are there. Remote `gitlab`.

GitHub `tomlawesome/orbit-site` (remote `origin`) is a push mirror GitLab
updates after every merge, and **GitHub Pages serves `main`** at
https://tomlawesome.github.io/orbit-site/ -- the mirror push is the
release. GitHub also keeps CodeQL. Nothing is filed, pushed or merged on
GitHub by hand.

- Mirror identity: a GitLab-generated SSH key held as a write-access deploy
  key on GitHub (as orbit-launcher).
- Issues #1 and #2 have the same number on both hosts; from #3 on, GitLab only.
- Agent credential: `glab` with `GLAB_CONFIG_DIR=~/.config/glab-claude` (or
  the Codex one) and `GITLAB_TOKEN` unset; the repo-local git credential
  helper for the `gitlab` remote is `!glab auth git-credential`.

## Branches: `dev -> main`, no `preview`

Two long-lived branches (owner decision, 2026-10-08, question 2b): `dev`
for work, `main` is what Pages serves. The shared three-branch flow's
`preview` exists so a release can be tested somewhere before it reaches
anyone; Pages serves one branch, so a `preview` here would deploy nowhere
and prove nothing. Do not add one, and do not "restore" it as an oversight.
`dev -> main` is by merge request, as a promotion.

## The nightly docs import commits to `main`

`import_docs` in `.gitlab-ci.yml` runs from a schedule on `main`, fetches
the markdown from the Orbit repositories and commits what changed straight
to `main`, so the docs stay nightly-fresh as they were on GitHub (owner
decision, 2026-10-08, question 1b). It pushes with `ORBIT_SITE_PUSH_TOKEN`,
a project access token whose bot user is allowed to push to `main`; it is
the one exception to "nothing lands on `main` but a promotion", and it only
ever touches `assets/docs/` and `assets/img/launcher/`. After it runs,
`main` is ahead of `dev` by that commit; the next `dev -> main` merge
request carries it, and a `main -> dev` back-merge is not needed because
the import is re-run, not merged.

## Verifying a change

    sh tools/ci/lint.sh                       # modules parse, files exist
    node tools/ci/serve.mjs                   # the site at :8787, as Pages serves it
    PLAYWRIGHT_ROOT=<playwright package dir> node tools/ci/journey.mjs   # Firefox

The journey is the gate's live check and is never optional. Locally,
playwright comes from a sibling checkout (orbit's
`node_modules/.pnpm/playwright@<version>/node_modules/playwright`); CI
installs it to match `$PLAYWRIGHT_IMAGE`. `BROWSER=chromium` for a second
engine.

The docs import by hand: `npm i --no-save --no-package-lock marked@18
sharp@0.34 && node tools/import-docs.mjs` (or `--from ../orbit` to read a
local checkout). Never commit `node_modules` or a `package.json`; the lint
refuses both.
