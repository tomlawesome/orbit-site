Security & privacy

Your household's data, on your terms

Orbit stores private household records and documents. Everything about how it's built, installed and run starts from that.

Self-hosted, by design

Orbit runs on a server you control. There is no hosted tenancy and no phone-home for your data. A household's workspace is never shown to an unauthenticated visitor, and a fresh instance stays unclaimed until you open the one-time link printed in its own container log.

Orbit listens on all interfaces by default so a reverse proxy can reach it. Set ORBIT_BIND_ADDRESS=127.0.0.1 to keep it to the host, and never expose its port directly to the internet. Plain HTTP is for loopback only.

What runs is what was published

  • Verified before it runs. The install command downloads a signed release manifest, checks it, and checks the SHA-256 of every file against it, with a second independent cosign signature when the tool is available. Nothing unverified is executed.
  • Digest-pinned. The installer resolves the published image to an immutable registry/repository@sha256:… digest and writes that to .env-orbit. A tag is only ever read to resolve it; a mutable reference is never deployed.
  • Assets from the image. Compose files, the scanner configuration and the operator scripts are taken from the same image digest that runs, so a compose file cannot drift from the image it configures.
  • Standard supporting images. PostgreSQL and ClamAV are the official images, pinned by digest. There is no custom database image.

Secrets stay out of the environment

The installer generates independent 256-bit session, database and document-encryption secrets and stores them under .orbit-secrets/, readable only by the installing host user. Compose mounts only the required files into each container under /run/secrets; the values are not injected into container environment variables. Existing secrets are preserved on later runs.

Configuration checks are value-free: configure.sh --check reports whether required settings are complete without printing them. Installer failure messages name fields, never values.

Documents: scanned, then encrypted

Every upload goes to ClamAV as a quarantined stream over a private Compose network. The scanner has no published port, no database credentials, no document volume and no Orbit secrets. Documents are then written to their volume as ciphertext only.

ClamAV is on by default. It can be disabled, but Orbit shows a persistent warning and marks files uploaded afterwards as unscanned.

The optional local processing services are kept apart too: Tika is attached only to a dedicated processing network with no route to the database, and Ollama is reachable only on the private Compose network, with no cloud models and no automatic downloads.

Accounts and sign-in

  • Local password accounts are always available; an OpenID Connect provider is optional and provider-neutral.
  • Opaque server-side sessions, PKCE, signed token validation, same-origin enforcement and CSRF protection.
  • Sensitive actions ask for recent authentication again.
  • Household APIs are authenticated and scoped. Household owners add members by display name, without exposing email addresses.

Yours to keep, and to recover

Backups and restores are scripts that ship with the deployment (scripts/backup.sh, scripts/restore.sh), with verification built in. A separate recovery bundle exports the key material, so a backup and its bundle together can bring a household back on a new host. Orbit never deletes or resets a database volume automatically.

Before every upgrade: create and verify a backup, and keep an owner-only copy of the exact pre-upgrade configuration beside it.

Reporting a vulnerability

Reports are taken seriously and handled privately. Please use the process in SECURITY.md, which also sets out which versions receive fixes. Deploy published images by immutable digest; that is the supported way to run Orbit.
